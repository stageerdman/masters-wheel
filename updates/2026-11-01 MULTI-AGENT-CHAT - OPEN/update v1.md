# Update — Mention-addressed multi-agent replies + real chat persistence

## Goal
Two related upgrades to `AIAssistant`, dictated together:
1. By default a chat replies with the one agent it's dedicated to
   (`session.agentId`). @mentioning one or more agents in a message
   overrides that default for that message only — exactly the mentioned
   agents reply (not the default agent too, unless it's also mentioned),
   each under their own avatar.
2. Chat sessions and their messages persist across reloads; `HistoryList`
   becomes real (reads real past chats, not `HISTORY_FIXTURES`).

This is AGENTS-ENGINE's originally-scoped "Phase 2 — Multi-agent, one
thread", refined now that Phase 1/1.5 settled the engine as the local
Claude Code CLI (not the Anthropic Messages API the original wiki.md
sketch assumed) — see "Design: multi-agent replies" below for how that
changes the recommended shape. Persistence was an explicit AI-Assistant
"to build" item in `FEATURES.md`, not previously scoped to an update;
it's bundled here because correct per-agent session continuity across
reloads is a prerequisite for the multi-agent design to mean anything
beyond a single in-memory session.

## Design: multi-agent replies, without corrupting any agent's native CLI session
Each agent's `claude -p --resume <id>` session is *that agent's own*
private conversation, maintained entirely by the Claude Code CLI itself —
not something this app constructs. The risk in a shared multi-agent
thread is feeding one agent's resumed session text that was actually
generated by a *different* persona, which would corrupt what "resuming"
even means for it.

Resolved by keeping sessions fully separate per agent, never shared:
- `ChatSession.claudeSessionId` (singular) becomes
  `claudeSessionIds: Record<agentId, string>` — one resumed CLI session
  per agent that has ever replied in this chat.
- Every `ChatMessage` from an agent now carries `agentId` (who actually
  said it), not just a session-wide "respondingAgent".
- When dispatching a reply for agent A, the text sent as that turn's
  `-p` argument is **not** the raw human message. It's everything in the
  shared transcript *since A's own last reply* (speaker-labeled: "You: …",
  "<OtherAgent>: …"), ending in the message just sent. A's own prior
  replies are never re-sent — `--resume` already carries those forward
  natively. An agent mentioned for the first time has no native history
  yet, so it gets the whole transcript so far instead of a delta.
- N mentioned agents → N `ask_agent` calls dispatched in parallel
  (`Promise.all`), each its own placeholder message/jobId/progress
  stream. No moderator/selector, no turn-taking within one send — matches
  the original wiki.md's explicit non-goal, now mapped onto CLI dispatch
  instead of parallel Messages API calls.

## Design: persistence
Follows the same precedent as `src/lib/agents` (one real file per entity
under `$APPDATA`, via `@tauri-apps/plugin-fs`, not a hosted DB) —
`src/lib/chat/storage.ts` writes one `chats/<sessionId>.json` per real
conversation. Draft ("pick someone") sessions are never written at
all — they're not real conversations, same reasoning `isDraftSession`
already uses to hide them from `HistoryList`. Streaming deltas are not
persisted token-by-token (would be excessive disk I/O); a reply is
written once, when it finishes or errors.

  `HistoryListItem` can reuse it for real `updatedAt` timestamps instead
  of a stored static string.
- `AIAssistant.script.ts` — `sendMessage` now resolves responders as
  "@mentions if any, else the dedicated agent, else block if ambiguous";
  dispatches all responders concurrently; loads real sessions from disk
  on first open (replacing `HISTORY_FIXTURES`, now deleted along with
  `AIAssistantWindow.data.ts`); persists every real mutation.
- `MessageList.tsx` resolves each message's author from `message.agentId`
  (falling back to the session's single resolved agent for
  pre-this-change messages that don't have one), so a thread with 2+
  replying agents shows each reply under its actual author.

## Decided
- Multi-agent v1 stays explicit-mention-only, parallel, no turn-taking —
  carried over from AGENTS-ENGINE's wiki.md, now implemented against the
  CLI engine instead of the Messages API it was originally sketched for.
- Each agent keeps a fully private resumed CLI session even inside a
  shared multi-agent thread; cross-agent awareness comes from injecting
  the transcript delta into the turn's message text, never from sharing
  or replaying one agent's session as another's.
- Draft sessions stay ephemeral/in-memory only, never written to disk.

## Follow-up pass — real-app bugs and feedback after trying it live
Four things dictated after the user's own click-through:

1. **"New chat" kept reopening the last chat with that agent instead of
   starting a fresh one.** `AgentPicker` (shown for a draft session) and
   `AgentStrip` (sidebar quick-access) shared one `onSelectAgent` handler
   that always reused an existing dedicated session for that agent —
   correct for AgentStrip ("jump to my chat with X"), wrong for
   AgentPicker ("start a *new* chat, happen to want X"). Split into two:
   `startChatWithAgent` (AgentPicker) always converts the current draft
   into a new session rather than searching for an existing one;
   `selectAgent` (AgentStrip) keeps the old reuse-if-exists behavior.

2. **Right-clicking a chat to delete it showed the menu *behind* the AI
   Assistant window**, unclickable. `AIAssistant.position.module.css`
   sets `z-index: 2147483000` ("the highest z-index in the app");
   `ContextMenu` only set `1000`. It already portaled correctly to
   `document.body` (fixed in CHAT-UX's own follow-up pass), but a portal
   only escapes the DOM tree, not the z-index stacking order — bumped to
   `2147483001`.

3. **The mentioned-agent "added to the conversation" chip was dropped
   entirely**, along with drag-and-drop (dragging an agent from the
   sidebar onto a chat to add them). Both fed the same
   `activeAgentIds`/`ActiveAgentChip` mechanism, which the user found
   confusing: it tracked who'd been *tagged or dragged in*, not who'd
   actually replied, and @mentioning the chat's own dedicated agent would
   add a redundant chip for someone already being talked to. Decided via
   explicit question: keep @mention's actual effect (who replies to that
   one message — the substantive part), drop the persistent roster/chip
   side effect entirely (the part that was "just visual," per the user's
   own framing). `ChatSession.activeAgentIds` is gone from the data model;
   `resolveActiveAgents` split into `resolveDedicatedAgent` (one, for "who
   am I talking to") and `resolveRespondedAgents` (every agent that's
   *actually* replied, computed from message authorship) — the latter is
   what `HistoryListItem` now shows instead of the chip row. The
   `@mention` picker itself (`Composer`) now renders real `AgentAvatar`
   photos instead of a plain initial badge — a separate small ask bundled
   into the same pass since it touched the same picker.

4. **Context/token usage tracking.** The CLI's `result` event already
   reports real `usage`/`modelUsage` data per call (verified by hand
   during the persona-break investigation above) — `assistant.rs`'s new
   `extract_context_usage` sums `input_tokens + cache_creation_input_tokens
   + cache_read_input_tokens + output_tokens` (together, the full prompt
   a `--resume`'d call was built from — exactly "how full this session is
   about to be on the next turn") against `modelUsage.<model>.contextWindow`.
   Stored per-agent as `ChatSession.contextUsage`, alongside
   `claudeSessionIds`. Surfaced in history's right-click menu (`ContextMenu`
   gained an optional `header` slot for this) via a new `ContextUsageGauge`
   element: a 0–100 bar plus a `formatTokenCount` label ("400k"), for
   whichever agent in that chat is closest to filling its window — picked
   by `summarizeContextUsage`. The bar's green→amber→red fill reuses the
   app's existing `--color-status-closed/postponed/failed` as a
   `color-mix` ramp rather than declaring new colors (see the element's
   own comment) — CLAUDE.md's category-palette carve-out exists for
   exactly this kind of case-but it's a *reuse* of the existing
   good/warning/bad vocabulary, not a new category.

Verified: `tsc --noEmit`, `npm run lint`, `npm run build`, `cargo check`
all clean; rebuilt and reinstalled to `/Applications/Master's Wheel.app`.

### Correction — the numbers weren't wrong, but a huge fixed cost was
User's own click-through flagged real-looking weirdness: a first reply
showed ~24k tokens, a second message to the same agent barely moved, and
adding a second agent (who has knowledge files) jumped the displayed
number to ~26k instead of looking like an accumulating total. Investigated
by reproducing against the raw CLI directly: a maximally trivial
`--system-prompt` ("You are Bob, reply only with: I am Bob.") plus a
2-token message still reported `input:2 + cache_creation:8596 +
cache_read:13039 + output:139 ≈ 21.8k tokens` — almost exactly the
observed Eli Wilde number, for content with no real persona/conversation
weight at all. That's a fixed floor the CLI adds to *every* call
regardless of content — tool/skill schema definitions (this install has
several skills/MCP servers registered) sent on every request even though
`--permission-mode dontAsk` with no `--allowedTools` already meant none
of them could ever actually be used. This explained both symptoms: the
floor swamps a short conversation's real growth (hence "barely moves"),
and a second agent's first-ever reply independently hits roughly the
same floor plus its own knowledge overhead (hence landing in a similar
but unrelated ballpark, not a running total — each agent's context is
a fully separate pool by this update's own design, see above).

Fixed, not just explained: added `--tools ""` to the CLI invocation,
which stops it from declaring any tool schemas at all. Re-tested the
identical minimal repro: same reply, `344` total tokens instead of
`21.8k` — a ~98% cut, with zero functional loss since no tool calling
was ever possible in this reply-only slice anyway. Verified against the
actual streaming flag set this app uses (`--output-format stream-json
--include-partial-messages --verbose`), not just the simpler one-shot
`json` format — streams and resolves identically.
